# LLM-authored HTML result summary

## Goal

Replace the fixed, rule-based prose in the combined HTML report's `Result summary` with an LLM analysis grounded in the recorded benchmark iterations. The summary must explain why an observed workflow used fewer tokens, where competing workflows spent more tokens, and why those costs arose from their actual tool interactions.

## Scope

This change affects the combined report generated by `pi_report.py` and the orchestration that regenerates it. It does not change benchmark execution, token accounting, per-model reports, tool isolation, or historical run artifacts. The analyst invocation's usage is report-generation overhead and must never be included in benchmark totals.

## Architecture

Add a report-analysis stage with three boundaries:

1. Evidence collection converts canonical summary rows and transcript events into a compact, serializable analyst input.
2. LLM analysis invokes pi without code-query tools once per testcase and requests schema-constrained JSON. Per-testcase calls keep large iteration traces within the analyst model's context window.
3. HTML rendering consumes only a validated cached analysis artifact.

The canonical cache is `artifacts/result-summary.json`. `pi_report.py` remains able to render deterministically from canonical benchmark artifacts plus this cache.

## Evidence input

For each testcase and tool/model row, collect:

- tool, version, model, and testcase identity;
- relevant aggregate metrics, including total, input, output, cache, reasoning, API calls, elapsed time, and tool-call count;
- transcript provenance path;
- every iteration's tool-call name and arguments;
- corresponding tool-result content;
- explicit structural markers for missing transcripts, empty results, command/tool errors, and truncated results when known.

The evidence must come from `summary.json` and recorded transcript JSON, never from generated HTML. Source-code words such as `error` or `failed` are not themselves failure evidence; failure classification uses tool-result structure or unmistakable diagnostics.

The payload may compact repeated or oversized result bodies, but it must preserve the details needed to explain token use: query scope, retries, pagination, broad graph/source responses, focused reads, empty probes, command failures, and repeated searches. Any compaction policy is deterministic and included in the cache fingerprint.

## Analyst contract

Run pi in one-shot JSON mode with no code-query tools. Select the analyst model from `PI_SUMMARY_MODEL`, falling back to `PI_MODEL`. The prompt instructs the model to return JSON only.

Each invocation produces one finding for its testcase. The cache combines the validated findings so the rendered output still contains one finding per testcase. Each finding:

- names the strongest observed workflow according to the supplied comparison;
- explains why that workflow was economical using concrete trace evidence;
- explains where each competing workflow spent additional tokens and why;
- distinguishes retrieval savings from follow-up validation or retry costs;
- avoids repeating metric values already visible in the report table;
- avoids fixed per-tool boilerplate and generic unsupported labels such as “indexed lookup”;
- does not infer correctness, completeness, or answer quality unless those properties are present in the evidence;
- states when trace evidence is missing instead of inventing an explanation.

The renderer escapes all analyst-authored text. The analyst cannot supply HTML.

## Cache and invalidation

`artifacts/result-summary.json` records:

- schema version;
- SHA-256 fingerprint;
- analyst model and provider information available from pi;
- generation timestamp;
- prompt/schema version;
- transcript provenance paths;
- validated findings.

The fingerprint covers the normalized analyst input, analyst prompt/schema version, selected model, and deterministic compaction settings. A matching cache is reused without an LLM call. Any relevant metric, transcript, model, prompt, schema, or compaction change invalidates the cache and triggers regeneration. Evidence normalization enforces a deterministic per-testcase size budget; over-budget evidence fails explicitly instead of being sent to the model.

Write the cache atomically through a temporary file followed by replacement so an interrupted analyst call cannot destroy the last valid artifact.

## Generation lifecycle and failures

Combined report generation first computes the fingerprint and checks the cache. On a miss it invokes the analyst, validates the JSON shape and testcase coverage, and writes the cache before rendering.

If analysis fails:

- a cache is reusable only when its fingerprint matches the current input;
- a stale cache is not presented as current analysis;
- when no matching valid cache exists, render a concise “LLM analysis unavailable” notice with the failure reason on stderr, rather than restoring fixed rule-based prose or inventing findings;
- benchmark data tables and recorded iterations still render normally.

Automatic analysis applies to normal `bench_pi.py` aggregation and direct `pi_report.py` execution. A cache hit must not require provider credentials or invoke pi.

## CLI and configuration

Use environment variables to avoid multiplying benchmark configuration files:

- `PI_SUMMARY_MODEL`: optional analyst model override;
- `PI_MODEL`: fallback analyst model already used by the benchmark workflow;
- `PI_BIN`: existing pi executable override.

Add a force-regeneration CLI option for deliberate re-analysis while preserving default content-addressed reuse. The option changes lifecycle behavior, not fingerprint semantics.

## HTML presentation

Keep `Result summary` in its existing collapsible `<details>` section. Render one finding per testcase, with short paragraphs that cover the winner's efficient behavior and the other workflows' observed costs. Tables remain the numeric source of truth; prose remains causal and qualitative.

Remove the current `_workflow_summary()` fixed sentence assembly and tool-specific rule templates from the summary path. Tool catalogue metadata remains renderer-owned and unchanged.

## Verification

The repository has no configured test runner, so this change will not add an unexecuted standalone `tests/` tree. Verification uses executable fixture/probe commands and the real canonical artifacts:

1. Compile all changed Python modules.
2. Feed a small temporary fixture with contrasting interaction traces into evidence collection and validate the normalized payload.
3. Use a controlled fake pi executable to prove a cache miss invokes the analyst, malformed JSON is rejected, and validated JSON is written atomically.
4. Re-run with unchanged inputs and prove the cache hit does not invoke pi.
5. Change a transcript and prove the fingerprint invalidates the cache.
6. Regenerate `artifacts/report.html` from the real artifacts.
7. Verify one finding exists per testcase, findings contain trace-specific causal explanations, analyst text is HTML-escaped, and legacy fixed phrases are absent.
8. Verify analyst usage does not alter any benchmark `summary.json`, `runs.json`, or table totals.

## Non-goals

- Scoring semantic correctness of benchmark answers.
- Using the analyst to modify benchmark metrics.
- Re-running benchmark cells when the summary changes.
- Supporting provider-specific HTTP clients in the first implementation.
- Keeping the current fixed prose as a fallback.
